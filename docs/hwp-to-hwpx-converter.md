## Problem Statement
Legacy `.hwp` (HWP 5.x, OLE binary) is opaque to Claude. `.hwpx` (OWPML, zipped XML) is editable text. The user wants a skill/script/binary that converts hwp→hwpx on macOS so that Claude can "make impeccable hwp editable": convert, edit the document, and hand back a file that looks right in Hangul, as `.hwpx` by default or `.hwp` when a recipient needs it ("Either, per job").

## What Makes This Cool
Claude edits a Korean government-style document and returns it with **proof**: a change report separating *conversion damage* (original .hwp vs converted .hwpx) from *intended edits* (hwpx before vs after), with page-level visual diffs rendered by Hancom itself. "Impeccable" becomes something you can inspect, not a promise. Timely: per Hancom's own blog (https://blog.hancom.com/en/?p=1184), the Ministry of the Interior and Safety requires HWPX on the On-Nara document system from May 2026, so this conversion is now routine.

## Constraints
- macOS only (Darwin 27, Apple Silicon assumed). Python 3.14 available. LibreOffice 26.2 present but cannot write HWPX. No JRE installed (`brew install openjdk` required).
- Hancom Office HWP for Mac 12.30 is installed but has **no AppleScript dictionary** (no `.sdef`); automation is System Events GUI scripting, which needs the Accessibility permission for the calling terminal/app.
- Licenses: neolord0 hwplib/hwpxlib/hwp2hwpx are Apache-2.0 (OK). pyhwpxlib is mostly BSL-1.1 (avoid). hwp2md is GPL-3.0 (avoid linking).
- Encrypted/password HWP files are not supported by hwplib; they must fail loudly.
- Implementation budget: at most 5 concurrent subagents (user instruction).

## Premises (agreed)
1. Deliverable is a Claude skill backed by a Mac CLI (`hwpkit`), not a standalone app.
2. Default engine is the Apache-2.0 hwp2hwpx Java converter, pinned to upstream `neolord0/hwp2hwpx` main at commit `62d95b980a` ("PR#18 반영", 2026-10-26) or later. PR #18 itself was closed unmerged, but the maintainer re-applied all 10 of its fixes (memo bodies, numbering, border/fill refs, compatibility/pagination) in that commit and confirmed on the PR. The May-2026 PyPI fat JAR predates this and is not used. The exact commit SHA is recorded in every `*.hwpkit.json`. Hancom Office for Mac is the high-fidelity fallback engine and the `.hwp` exporter, driven by GUI scripting.
3. **(Revised after cold read)** "Verified" means: (a) content inventory diff (paragraph text, tables with cell counts, images, memos, footnotes, numbering) between the original HWP and the output, AND (b) Hancom-rendered PDF page diff. Reported as two diffs: conversion damage vs intended edit. Structural validity and "opens in Hancom" are necessary, not sufficient. Exact gating rules are in "Verification model" below.
4. The skill ships safe-edit rules and helpers for hwpx XML: keep `charPrIDRef`/`paraPrIDRef`/`borderFillIDRef` pointing at existing `header.xml` entries (add new ones rather than mutate shared ones), strip stale `<hp:linesegarray>` from edited paragraphs so Hancom re-lays them out, keep `mimetype` first and stored uncompressed when re-zipping, update `content.hpf` manifest for added binaries.

## Approaches Considered
### Approach A: Headless core
Python CLI + pinned hwp2hwpx JAR + hwplib-based inventory diff + SKILL.md edit rules. No Hancom. Effort S. Chosen as milestone 1, not as the end state (no layout proof, no .hwp export).
### Approach B: Verified edit loop (CHOSEN)
A, plus Hancom GUI automation, `hwpkit edit` patch helpers, PDF page diff, two-stage change report with rollback. Effort L.
### Approach C: Hancom-first. Rejected: GUI-bound for every conversion (estimated ~10 s/file, to be confirmed by the Assignment timings), no parallelism, fragile on every Hancom update. B also uses Hancom, but only for render/export/fallback, not for every conversion.

## Recommended Approach
Approach B, built A-first.

**Layout** (proposed location `` in this repo):
```
hwpkit/
  pyproject.toml            # uv-managed; deps: lxml, pymupdf, pillow
  hwpkit/cli.py             # convert | inspect | diff | edit | render | export | verify
  hwpkit/engine_java.py     # runs ~/.local/share/hwpkit/hwp2hwpx-all.jar (or $HWPKIT_JAR) via `java -jar` (JAVA_HOME from brew openjdk)
  hwpkit/engine_hancom.py   # System Events GUI scripting via osascript (open, Save As, Export PDF)
  hwpkit/inventory.py       # content inventory for .hwp (via a tiny Java dumper on hwplib) and .hwpx (lxml)
  hwpkit/hwpx_edit.py       # safe-edit helpers: set_text, set_cell, add_charpr, strip_lineseg, repack
  hwpkit/render_diff.py     # PDF → PNG (PyMuPDF) → per-page pixel diff, page-count check
  hwpkit/report.py          # two-stage change report (markdown + JSON)
  java/                     # Gradle build: hwp2hwpx fat JAR + InventoryDump main, pinned upstream commit
skill/SKILL.md              # Claude skill: when to use, workflow, edit rules, verify gate
```

**Job directory (no in-place mutation, rollback by construction)**
Every conversion creates `<name>.hwpkit/` next to the output:
```
<name>.hwpkit/
  00-original.hwp        # byte copy of the input, never touched
  01-converted.hwpx      # convert output, immutable after creation
  02-edit-001.hwpx       # each `edit` call writes the next numbered snapshot
  02-edit-002.hwpx
  edits.jsonl            # edit manifest: one line per op (see below)
  meta.json              # engine, hwp2hwpx commit SHA, hwpkit version, input sha256
  report.md / report.json
```
`hwpkit edit` reads the latest snapshot and writes a new one; it never overwrites an existing file. `hwpkit rollback <job> [--to N]` copies snapshot N (default: previous; N=0 means `01-converted.hwpx`, whose keymap is the identity) to a new head snapshot, writes the new head's keymap as a copy of `keymap-N.json`, and appends `{"seq":..,"op":"rollback","to":N,"after_sha":<sha256 of the restored snapshot>}` to `edits.jsonl`. Ops with snapshot index greater than N become inactive: stage 2 builds its declared-target list only from ops still in effect after the last rollback, and the UNTRACKED_MODIFICATION check compares against the rollback line's `after_sha`. Skill rule: if `verify` fails, Claude runs `rollback`, reports the failing objects to the user, and does not deliver the file.

**Edit ops and addressing (milestone set)**
Targets are addressed by **container paths**, the same grammar the inventory uses for `key`. A path is a sequence of steps from a section root down to the object:
- `s0/p12`: paragraph 12 in section 0 body.
- `s0/t2/r1c3/p1`: paragraph 1 inside cell (row 1, col 3) of table 2 in section 0 (logical grid coordinates; a merged cell is addressed by its top-left).
- `s0/t2/r1c3/t0/r0c0/p0`: nested table inside that cell.
- `s0/hd0/p0`, `s0/ft0/p0`: header/footer paragraphs; `s0/m3/p0`: memo 3 body; `s0/fn2/p0`: footnote 2 body.
Ordinals count only same-type siblings in the same container. Paths are **positional, not stable**: an insert or delete shifts later siblings. Stability across snapshots comes from the keymap below, not from the paths.

**Keymap (alignment across snapshots)**
Each snapshot `02-edit-N.hwpx` has a sidecar `keymap-N.json` mapping every current path to its baseline path in `01-converted.hwpx`, or to `new:<seq>` for objects created by op `seq`. `hwpkit edit` maintains it: each op is applied to the previous keymap (an insert adds `new:<seq>` and shifts later siblings; a delete removes the entry). Ops in `edits.jsonl` record their target **in baseline coordinates** (resolved through the keymap) plus the current path at the time of the edit. If the head snapshot's sha256 does not equal the last `after_sha` in `edits.jsonl` (the file was changed outside hwpkit), `verify` exits 3 with `UNTRACKED_MODIFICATION`.
- `set-text <para-path> <text>`: replace the run text of one paragraph at any container path (body, cell, nested cell, header/footer, memo, footnote), keeping the first run's `charPrIDRef`.
- `set-cell <cell-path> <text>`: shorthand for `set-text <cell-path>/p0` when the cell has exactly one paragraph; otherwise refuses (exit 13 `AMBIGUOUS_TARGET`) and asks for a paragraph path.
- `insert-para-after <para-path> <text> [--like <para-path>]`: new paragraph in the same container, cloning the style refs of `--like`.
- `delete-para <para-path>`: deletes only plain paragraphs. A paragraph containing any control or anchor (inline image, equation, shape, nested table, memo or footnote/endnote anchor, field) is refused with exit 14 `ANCHORED_CONTENT`, naming the anchored objects, so a delete never removes undeclared objects or shifts memo/footnote ordinals.
A path that does not resolve exits 13 `AMBIGUOUS_TARGET` with the nearest valid paths listed.
- `set-charpr <target> --bold/--italic/--size N/--color #RRGGBB`: adds a new `charPr` entry to `header.xml` (never mutates a shared one) and repoints the target.
Each op appends `{"seq":N,"op":..,"target":..,"before_sha":..,"after_sha":..}` to `edits.jsonl`. That manifest is the declared-target list.

**CLI contract**
- `hwpkit convert in.hwp [-o out.hwpx] [--engine java|hancom|auto]`: creates the job dir. `auto` = java, then hancom if the conversion inventory diff is non-empty AND the hancom engine is available; otherwise it keeps the java output and reports the loss (exit 3).
- `hwpkit inspect file.(hwp|hwpx) [--json]`: content inventory.
- `hwpkit diff a b`: inventory diff; exit 3 on any lost/changed object.
- `hwpkit edit <job> --op ...` and a Python API for Claude; strips lineseg on touched paragraphs, validates ID refs, repacks to the next snapshot, appends the manifest.
- `hwpkit render file -o file.pdf`: Hancom PDF (see capability fallback).
- `hwpkit export <job> --to hwp`: Hancom Save As .hwp of the head snapshot into `<job>/90-export.hwp`, then automatically runs the export check (below).
- `hwpkit verify <job>`: runs all applicable stages, writes the report.
- `hwpkit doctor`: checks JAR, JAVA_HOME, Hancom presence, Accessibility grant, and recorded Hancom capabilities.

**Exit codes**: 0 verified; 2 verified-partial (inventory stages passed, render stages skipped: Hancom unavailable, no Accessibility grant, or GUI timeout); 3 damage or out-of-scope change found; 10 encrypted/password-protected input; 11 corrupt or unparseable input; 12 unsupported input (not HWP 5.x / HWPX, e.g. HWP 3.0); 13 AMBIGUOUS_TARGET (edit path does not resolve or is ambiguous); 14 ANCHORED_CONTENT (delete refused); 22 HANCOM_BUSY (lock wait timed out); 20 environment error (JAR missing, Java missing); 21 Hancom cleanup failed (a hwpkit window could not be closed). Every nonzero exit prints one line `hwpkit: <CODE_NAME>: <file>: <reason>` to stderr.

**Verification model** (what gates the exit code)
- Stage 1, conversion damage (`00-original.hwp` vs `01-converted.hwpx`): inventory diff must be empty. **Gates.** Render diff (Hancom PDF of the .hwp vs of the .hwpx): page count must match and every page must be under the calibrated pixel threshold. **Gates** when Hancom is available.
- Stage 2, intended edits (`01-converted.hwpx` vs head snapshot): objects are aligned through the head keymap (baseline path ↔ current path). Container objects (cell, memo, footnote, endnote, header, footer, table) are compared only on their own fields (spans, anchors, sizes), never on derived text aggregated from descendants, so editing a paragraph inside a cell changes only that paragraph object. Every baseline object whose fields changed must be a declared `set-*` target; every baseline object absent from the head must be a declared `delete-para` target; every `new:<seq>` object must come from a declared insert. Anything else is an out-of-scope change. **Gates.** Render diff: a text edit legitimately reflows later lines and pages, so pages from the first edited page onward are **advisory** (the report shows the page-count delta and per-page diffs). Pages *before* the first edited page must be under the same-format threshold; that part **gates**.
  - *Finding the first edited page*: for each declared target, take its pre-edit normalized text from `01-converted` and search the `01-converted` PDF with PyMuPDF `search_for`. If there are several hits, disambiguate with the text of the previous non-empty sibling paragraph, which must appear on the same or the preceding page. The first edited page is the minimum over targets (an insert uses its anchor paragraph). If any target is empty, not found, or still ambiguous, the "before the edit" check cannot be computed: the whole stage 2 render check becomes advisory, the report says `EDIT PAGE UNKNOWN: <target>`, and `verify` exits 2 (layout not fully verified), never 0.
- Stage 3, export check (only after `export --to hwp`): inventory diff of `90-export.hwp` vs head snapshot must be empty. **Gates.** Render: page count must match (**gates**), and each page must be under the **cross-format threshold** (**gates** when calibrated, see below). The skill must not hand back a `.hwp` unless stage 3 passed with exit 0 or, if the user accepts, exit 2 with the reason shown.

**Thresholds and calibration** (`make calibrate`, rerun after any Hancom update)
- *Same-format threshold*: Hancom renders the same file twice; the max per-page pixel diff over the corpus times 1.5. Used for comparisons where both sides are the same format (stage 2).
- *Cross-format threshold*: for each corpus `.hwp`, Hancom saves its own `.hwpx` (Save As), and both are rendered. Calibration pairs are first audited: a pair whose page counts differ, or whose inventories differ, is excluded and listed as an outlier (Hancom's own Save As is not assumed lossless). The cross-format threshold is the 95th-percentile per-page diff over the remaining pairs times 1.5, capped at an absolute ceiling of 2% of page pixels; if the computed value exceeds the ceiling, or fewer than 3 pairs survive the audit, calibration fails and the state is "uncalibrated". Every report prints both threshold values, the Hancom version they were measured on, and the outlier list. Used by stage 1 (hwp vs hwpx) and stage 3 (hwpx vs hwp). This answers Open Question 3: cross-format rendering differences are absorbed by a measured threshold, not assumed zero.
- If Hancom cannot Save As HWPX, the cross-format threshold cannot be calibrated: cross-format render comparisons keep page count as the only gating check, per-page diffs become advisory, the report says `CROSS-FORMAT THRESHOLD UNCALIBRATED`, and verify exits 2 at best. Stage 1's baseline stays `00-original.hwp` (there is no Hancom-written hwpx to switch to).
- Both thresholds are stored in `~/.config/hwpkit/capabilities.json` with the Hancom version they were measured on; a Hancom version mismatch means "uncalibrated" until `make calibrate` reruns.
- Degraded mode: if Hancom is unavailable, render stages are skipped, the report carries the line `RENDER NOT VERIFIED: <reason>`, and the exit code is 2. Skill rule: Claude tells the user "content verified, layout not verified (<reason>)" and never says "verified" alone. Milestone 1 (Java-only) therefore always ends at exit 2 at best, and says so.

**Inventory schema** (shared by both extractors)
One JSON document: `{"objects":[...]}`, ordered by document order. Each object: `{"key", "type", "fields"}`.
- `type` ∈ `para | cell | table | image | memo | footnote | endnote | header | footer | equation | shape`.
- `key`: the container path defined under "Edit ops and addressing" (e.g. `s0/t2/r1c3/p1`). Ordinals count only objects of the same type in the same container, so an image insert does not renumber paragraphs. Both extractors must emit nested tables, header/footer, memo and footnote bodies as their own containers.
- Compared fields: para/cell: normalized text, list level, numbering *format id* (not the rendered number); table: rows, cols, list of merged spans `(r,c,rowspan,colspan)`; image: sha256 of binary, display size in HWPUNIT; memo/footnote/endnote: normalized body text and anchor paragraph key; header/footer: normalized text and apply-page type; equation: script string; shape: kind + size.
- Normalization (both sides): Unicode NFC; collapse runs of whitespace to one space except preserve explicit line breaks as `\n`; drop zero-width and field-control characters; tabs as `\t`; numbering compared by format id + level, never by rendered text; HWPUNIT sizes compared with ±1 tolerance.
- Self-check (milestone-1 gate): for each corpus file, `inspect(original.hwp)` must equal `inspect(Hancom-saved .hwpx of the same file)`. Any mismatch is an extractor bug, fixed before the Java engine is judged.

**Hancom automation rules**
- Explicit per-step timeouts (default 30 s); one job at a time behind a lock file in `~/.cache/hwpkit/hancom.lock`.
- **User-safety guard**: before starting, list Hancom's open windows. If any document window is open that hwpkit did not open, refuse with exit 2 (render skipped) and the message "Hancom has open documents; close them or pass --allow-open-docs". With `--allow-open-docs`, hwpkit still never sends keystrokes, close or "Don't Save" to a window it did not open.
- Before every keystroke or menu action, re-resolve and raise the target window by its exact document title (the job file's unique name, e.g. `hwpkit-<random>-01-converted.hwpx`); if the frontmost window differs after raising, abort the step (focus loss) and exit 2.
- hwpkit closes only windows it opened: after a successful save/export, or during abort cleanup.
- **Abort cleanup** (on GUI timeout, focus loss, osascript error, or SIGINT): (1) if a sheet or modal dialog is attached to a hwpkit-titled window, press its Cancel button (by accessibility role, not by keystroke to the frontmost app); (2) close every hwpkit-titled window and answer "Don't Save" for that window only (they hold only temp copies inside the job dir); (3) release the lock. If a cleanup step itself fails, print the window title still open and exit 21.
- **Lock**: `~/.cache/hwpkit/hancom.lock` holds `{pid, started_at, heartbeat_at, job}`; the holder refreshes `heartbeat_at` every 5 s and before each GUI step. A new run reclaims the lock only when the PID is not alive, or the PID is alive but `heartbeat_at` is older than 120 s (hung). Never on age alone. When the lock is held by a live, heartbeating process, the new run waits up to `--lock-wait` (default 300 s), then exits 22 `HANCOM_BUSY`. Leftover-window cleanup runs only while holding the lock. Parallel subagents therefore serialize on Hancom instead of tearing each other down.
- **Leftover windows**: hwpkit window titles always start with `hwpkit-` plus a random token. At startup, `hwpkit-*` windows are treated as hwpkit's own leftovers (cleaned with abort cleanup), never as foreign documents, so a crash cannot wedge later runs. A user document is never named this way.
- Detect "Accessibility not granted" (osascript error -1719/-25211) and print the exact System Settings path.
- Menu labels may be Korean or English depending on locale; resolve them from `capabilities.json` recorded from the Assignment baseline, never hardcode one locale silently.

**Hancom capability fallback** (if the Assignment shows a capability is missing in Hancom Mac 12.30)
- No HWPX in Save As: `--engine hancom` is disabled; `auto` keeps the Java output and reports loss (exit 3); success criterion "5/5 with auto" drops to "4/5 with zero damage, remaining file reported precisely".
- No PDF export menu: render via File > Print > PDF > Save as PDF (macOS print dialog), scripted the same way; if that also fails, all render stages are skipped and verify exits 2.
- No Save As .hwp: `export --to hwp` is disabled and `.hwp` delivery is out of scope until resolved; documented in `doctor`.
`hwpkit doctor` writes the detected capabilities to `~/.config/hwpkit/capabilities.json`.

**Mac compatibility specifics**: `brew install openjdk` and set `JAVA_HOME=$(brew --prefix openjdk)/libexec/openjdk.jdk/Contents/Home` inside the CLI (do not require a system Java symlink); handle Korean NFD filenames from Finder (normalize to NFC for lookups); paths with spaces in osascript must be passed as `POSIX file` arguments, never string-interpolated into script source; work on copies in a temp dir to avoid Hancom file locks and iCloud placeholders.

## Success Criteria
- On a 5-document corpus (merged tables, images, memo, numbered lists, headers/footers): `hwpkit convert` + `hwpkit verify` reports zero conversion damage for at least 4/5 with the Java engine, and 5/5 with `--engine auto`.
- One real edit per document (a paragraph and a table cell) passes `verify` with the change report listing only the declared targets.
- `hwpkit export --to hwp` produces a .hwp that passes verification stage 3 (inventory-equal and render-equal to the edited hwpx).
- Fresh-machine setup on macOS is `brew install openjdk uv`, then `make install`, plus one Accessibility grant. `hwpkit doctor` exits 0 afterwards.
- The Claude skill makes Claude run `verify` before declaring any edit done, and report exit 2 as "layout not verified".

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: MAX_ITERATIONS

### R3-1 — consistency (blocking)

**Problem**

> Edits now target paragraph paths such as `s0/t2/r1c3/p1`, and `set-cell` is shorthand for `set-text <cell-path>/p0`, so the declared target is the paragraph. But the inventory also emits the enclosing `cell` object with its own normalized text, and memo, footnote and header/footer objects carry their body text too. Editing a paragraph inside them changes the parent object's fields, and the parent is not a declared `set-*` target. Stage 2 flags it as an out-of-scope change, so every table-cell edit (required by the success criterion) and every memo, footnote or header edit fails verify.

**Remedy**

> State that a container object (cell, memo, footnote, endnote, header, footer) whose only field changes come from declared descendant targets counts as in scope. Alternatively, drop derived text from container objects and compare only their own fields, such as spans and anchors.

### R3-2 — completeness (blocking)

**Problem**

> Deleting a paragraph also removes everything anchored in it: inline images, equations, shapes, a nested table, and the memo or footnote whose anchor it holds. Those baseline objects are absent from the head but are not themselves declared `delete-para` targets, so stage 2 reports a legitimate delete as an out-of-scope change. Removing the anchor also shifts later memo and footnote ordinals, which the keymap rule ("a delete removes the entry") does not cover.

**Remedy**

> Either make `delete-para` refuse paragraphs that contain controls or anchors (with a defined exit code), or define that the keymap records the deleted paragraph's descendants and anchored objects as deleted with the same `seq`, renumbers the affected sibling ordinals, and that stage 2 accepts them.

### R3-3 — completeness (blocking)

**Problem**

> `rollback` copies snapshot N to a new head and appends a `rollback` line, but the design does not say whether that line carries an `after_sha`, whether the matching `keymap-N.json` is copied to the new head, or whether ops after N stay in the declared-target list. As written, `verify` right after a rollback can exit 3 `UNTRACKED_MODIFICATION`, align objects through a keymap that does not match the head, or accept changes from ops that were rolled back.

**Remedy**

> Specify that rollback writes the new head's keymap as a copy of `keymap-N.json`, records `after_sha` (the restored snapshot's hash) in its manifest line, and that stage 2 builds its declared-target list only from the ops still in effect after the last rollback.

### R3-4 — completeness (blocking)

**Problem**

> A new run reclaims the lock when `started_at` is older than 10 minutes, even if the holder's PID is still alive, and then runs abort cleanup, which closes every `hwpkit-*` window. A legitimate long job (several 30 s steps on a large document, or a calibration run) is then torn down by a second run, and two runs drive Hancom at once. Parallel subagents (Next Steps) make concurrent runs likely. The design also does not say what a run does when the lock is held by a live, recent process (wait, retry, or exit with which code), or whether the startup cleanup of leftover `hwpkit-*` windows happens only after the lock is acquired.

**Remedy**

> Reclaim only when the PID is dead, or when the holder is stale by a heartbeat that the running job refreshes, never on age alone. Define the behavior when the lock is busy (wait with a timeout, then a named exit code), and state that leftover-window cleanup runs only while holding the lock.

### R3-5 — feasibility (blocking)

**Problem**

> The cross-format threshold is the max per-page diff over the corpus times 1.5, assuming that Hancom's own hwp to hwpx Save As is lossless and layout-identical. That assumption is unsupported. If Hancom's save shifts a line break or a page on even one corpus file, the max absorbs a real layout change, and the threshold that gates stages 1 and 3 becomes too loose to catch the damage it exists to detect. Nothing bounds or audits the calibrated value.

**Remedy**

> Exclude calibration pairs whose page counts or inventories differ, report per-file outliers, set an absolute ceiling (or use a high percentile with a cap) beyond which calibration fails as uncalibrated, and print the threshold value and the Hancom version in every report.

### R3-6 — consistency (minor)

### R3-7 — feasibility (minor)
